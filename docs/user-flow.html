gemspot 기능 명세 초안

메인 플로우

웹으로 배포하므로 시작점은 사용자가 이미 저장해 둔 이미지를 올리는 것이다.

  1. 이미지 업로드

    확정 담당 · 상욱
    화면 · 업로드
    • 업로드 버튼을 누르면 파일 선택창이 열리고, 앨범에 저장해 둔 스크린샷을 고른다
    • 한 번에 한 장만 올린다. 여러 장 선택은 두지 않는다
    • 기본은 웹 표준 파일 업로드로 처리한다
    • 모바일 웹에서 공유하기로 스크린샷 화면을 바로 받을 수 있으면(Web Share Target) 그렇게 구현한다 확인 필요

    파일 업로드 — 4단계

    1. 인스타그램에서 스크린샷을 찍는다
    2. 홈 화면으로 나가 gemspot을 연다
    3. 업로드 버튼을 누른다
    4. 앨범에서 아까 그 사진을 찾아 고른다

    공유하기 — 2단계

    1. 인스타그램에서 공유하기를 누른다
    2. 공유 목록에서 gemspot을 고른다

    앱을 설치하지 않아도 되고, 앨범에서 사진을 다시 찾는 과정이 사라진다. 다만 홈 화면에 설치(PWA)해야 공유 목록에 뜨고 기기 · 브라우저를 탄다.

  2. 이미지에서 주소 추출

    확정 담당 · 상욱

    이미지를 VLM에 그대로 넘겨 상호명과 주소를 받는다. 글자만 떼어 읽는 OCR을 쓰지 않는 이유는, 화면에 적힌 것이 주소인지 해시태그인지 가게 이름인지를 가르는 일이 결국 문맥 판단이기 때문이다. 받은 결과를 STEP 3으로 넘긴다. 여기서 말하는 성공 · 실패는 VLM이 상호명과 주소를 읽어냈는가이지, 지도에 핀이 찍혔는가가 아니다.

    • 한 장에 가게가 여러 곳 담긴 게시물이 있다(피롤츠 · 파브리키친이 한 화면). 주소가 둘 이상 나오면 각각을 따로 뽑는 쪽으로 구현한다 — 올리는 이미지는 한 장이지만 그 안의 가게는 여러 곳일 수 있다 확인 필요

    성공 — 주소를 읽어냈다

    1. 피롤츠 커피하우스 · 서울 용산구 한강대로 56-1, 2층
    2. 파브리키친 · 서울 용산구 한강대로15길 23-6
    3. 익스프레스노원바이미라쥬 · 서울 노원구 화랑로 608

    Geocoding에 넣어 좌표가 나올 가능성이 높다. 실제 변환은 STEP 4에서 한다.

    실패 — 지역명과 가게명뿐이다

    1. 한강동 · 용산역 · 용산구
    2. 에그앤플라워 · 용산동2가

    번지가 없어 가게 위치를 특정할 수 없다. 동 이름만으로 핀을 찍으면 엉뚱한 곳에 꽂히므로 실패로 보내 직접 입력을 받는다.

  3. 추출 결과 목록

    확정
    화면 · 결과 목록

    STEP 2에서 넘어온 데이터를 받아 성공했는지 실패했는지 알럿으로 먼저 알린다. 그다음 성공한 건과 실패한 건을 보여준다.

    • 보여주는 형태는 페이지 · 모달 · 바텀시트 중 하나로 푼다 확인 필요
    • 성공과 실패를 가르는 방법도 탭 · 목록 분리 · 필터 중에서 정한다 확인 필요
    • 추출 결과는 바로 저장되지 않는다. 이 화면에서 사용자가 확정해야 스팟이 된다
    • 목록의 각 건마다 저장 · 삭제를 고를 수 있다
    • 여러 건을 한 번에 저장하거나 삭제할 수 있어야 하는지 확인 필요

    성공한 건

    주소가 잡힌 이미지들. 뽑힌 주소가 맞는지 사용자가 보고 저장할지 버릴지 고른다. 저장을 고른 건만 STEP 4로 넘어간다

    실패한 건

    VLM이 주소를 읽어내지 못한 이미지를 모아 본다. 주소를 직접 입력하거나, 목록에서 삭제한다. 재시도는 두지 않는다 — 같은 사진을 다시 읽어봐야 결과가 달라지지 않는다. 직접 입력한 건도 성공한 건과 같이 STEP 4로 보낸다

  4. 확정한 스팟 저장

    확정
    • 화면이 아니다. 확정된 건을 서버로 보내는 내부 처리다
    • STEP 3에서 확정한 주소를 좌표로 바꾼다. VLM이 뽑은 주소든 직접 입력한 주소든 여기서 한 번에 검증한다 — 좌표가 나오지 않으면 저장하지 않는다
    • 상호명 · 주소 · 좌표를 서버로 보낸다
    • 별도 백엔드 없이 Next.js 하나로 처리한다
    • 어디에 저장할지 확인 필요
    • 카테고리 분류를 함께 저장할지 미정 — AI가 분류하고 목록 필터로 쓰는 값이다
    • 성공하면 STEP 5로 넘어간다. 실패하면 STEP 3에 머문 채 알럿이나 토스트로 오류를 띄워 무엇이 잘못됐는지 눈에 보이게 한다

    네이버 Geocoding API에 뽑아낸 주소 문자열을 query로 넘기면 addresses[]가 온다. 핀을 찍는 데 쓰는 값은 x(경도) · y(위도)이고 둘 다 문자열로 온다. 함께 오는 roadAddress · jibunAddress는 저장용, addressElements의 SIDO · SIGUGUN은 지역 필터용으로 쓸 수 있다. meta.totalCount가 0이면 결과가 없다는 뜻이므로 저장하지 않고 오류를 띄운다.

  5. 지도에 핀 찍기

    확정 담당 · 가은
    화면 · 지도
    • 저장이 성공하면 이 화면으로 넘어와, 저장된 내용을 지도와 함께 다시 확인한다
    • 저장된 좌표에 핀을 찍고, 지도를 그쪽으로 이동시킨다
    • 화면 아래에는 저장된 정보를 함께 띄운다
    • 닫으면 초기 화면으로 돌아간다
    • 방금 찍은 핀만 보여준다. 저장된 핀 전체는 "내 스팟 지도"에서 본다
    • 내 위치를 함께 보여줄지 미정 — 기능으로 넣을지부터 정해야 한다

메인 플로우 외 세부 기능

스팟을 저장한 뒤, 각각 따로 들어가는 화면이다.

  • 내 스팟 지도 — 저장된 핀 보기

    담당 미정
    화면 · 내 스팟 지도
    • 저장해 둔 스팟들을 지도 위 핀으로 한눈에 본다
    • 핀을 고르면 그 스팟의 상세로 간다 미정
    • 기본은 1인 사용 확정

  • 필터 · 카테고리

    미정 · 담당 없음

    카테고리로 스팟을 걸러 보는 화면. 지도 보기와 분리했다. 지금은 맡은 사람이 없어 구현 시점이 정해지지 않았다.

  • 스마트 동선 가이드

    확정 담당 · 화균, 주희(고민중)
    화면 · 동선 만들기

    "오늘 2시부터 4시까지 성수동에서 카페 들르면서 걷고 싶어"처럼 말로 요청하면, 저장된 스팟 중 그 조건에 맞는 곳만 골라 실측 도보 시간이 맞는 순서로 여정을 제안한다. 스크랩만 쌓이고 안 가게 되는 문제를 폼이 아니라 한 문장으로 풀려는 것이다. 제안은 시작점이고, 사용자가 빼고 순서를 바꿔 확정한다.

    1. 말로 요청 자연어 한 문장 — 시간 · 동네 · 취향 · 꼭 갈 곳이 섞여 있어도 된다
    2. 요청 해석 LLM — 시간대 · 동네 · 카테고리 선호 · 필수 스팟으로 구조화. 빠진 건 되묻는다
    3. 후보 고르기 규칙 — 동네 반경 안 + 해석된 시간대에 맞는 카테고리만
    4. 순서 · 이유 제안 LLM — 후보와 거리표를 보고 어디를 어떤 순서로, 왜
    5. 도보 실측 TMAP 보행자 경로 — 구간별 실제 거리 · 시간
    6. 시간 맞추기 규칙 — 체류 + 이동을 쌓아 종료 시각을 넘으면 뒤에서 뺀다
    7. 다듬기 · 경로 그리기 빼기 · 순서 바꾸기 후 지도에 경로선과 번호
    • LLM이 문장에서 뽑는 것은 넷이다 — 시간대, 동네, 카테고리 선호("카페 들르면서"), 꼭 갈 스팟. 해석 결과를 화면에 보여 주고 사용자가 고칠 수 있게 한다. 시간대나 동네를 잘못 읽으면 동선 전체가 틀리는데, 그 오류는 결과만 보고는 알기 어렵다 확정
    • 시간대나 동네가 문장에 없으면 되묻는다. 기본값으로 추측해 채우지 않는다 — "지금부터 두 시간"처럼 상대 표현은 요청 시각 기준으로 푼다
    • 해석된 시간대가 카테고리를 거른다 — 14~16시면 밥집은 빠지고 카페 · 상점 · 구경거리만 후보다. "카페 위주" 같은 선호는 후보를 거르지 않고 가중치로만 쓴다. 카테고리별 적합 시간대 표와 기본 체류 시간(예: 카페 40분 · 밥집 60분)은 정해야 한다 미정
    • 이 기능은 스팟에 카테고리가 있어야 돈다. STEP 4의 "카테고리 분류를 함께 저장할지"가 여기서는 미정이 아니라 필요조건이다. AI가 붙인 카테고리를 사용자가 고칠 수 있어야 한다 확인 필요
    • 순서는 LLM이 제안하고 "왜 이 순서인지" 한 줄 이유를 함께 낸다. LLM은 지리를 계산하지 못하므로 후보 간 직선거리표를 함께 준다 — 이름만 주면 동선이 지그재그가 된다 확정
    • 이동 시간과 거리는 TMAP 보행자 경로 API 실측으로 낸다. 네이버 Directions는 자동차 경로 중심이라 도보에 맞지 않고, 카카오는 도보 경로 API가 없다. 직선거리는 실측이 실패한 구간의 추정치로만 쓴다 확정
    • 제안이 종료 시각을 넘으면 LLM에 한 번 다시 묻고, 그래도 넘으면 꼭 들를 스팟이 아닌 마지막 스팟을 뺀다. 빠진 스팟은 화면에 보여 준다
    • LLM이 실패하면 규칙만으로(가까운 곳부터) 순서를 만들고, 화면에 "규칙 기반"으로 표시한다. 조용히 대체하지 않는다
    • 출발점은 문장에서 해석한 동네 이름을 STEP 4와 같은 Geocoding으로 좌표로 바꾼다. 내 위치 · 지도에서 직접 찍기는 그다음이다 미정
    • 제안 뒤에는 사용자가 다듬는다. 빼면 뒤 번호가 당겨지고 순서를 바꾸면 도보 시간을 다시 실측한다. 지도에는 경로선과 출발 → 1 → 2 번호를 그린다
    • 방문한 곳은 후순위로 밀어야 하지만, 방문 기록 기능이 후순위라 그때 붙인다 후순위
    • 오르막 회피 · 구경하기 좋은 길 선호는 1차에서 뺀다. TMAP은 고도를 주지 않고, LLM이 거리 분위기를 아는 것처럼 말하면 지어낸 것이다. 고도 데이터 소스가 정해지면 붙인다 후순위
    • LLM 제공자와 SDK 미정 — 어느 쪽이든 추천 엔진 바깥의 어댑터 한 파일에서만 바뀐다

    성공 — 동선이 나온다

    1. "2시부터 4시까지 성수동, 카페 들르면서" → 해석: 14:00~16:00 · 성수동 · 카페 선호
    2. 14:00 출발 → 14:08 편집숍 A(20분) → 14:34 카페 B(40분) → 15:19 서점 C(30분) → 15:49 끝
    3. 총 도보 21분 · 1.6 km. 밥집 D는 시간대 밖이라 후보에서 빠짐

    해석과 순서 · 이유는 LLM이, 구간별 시간은 TMAP 실측이 낸다.

    실패 — 제안하지 않는다

    1. "성수동 걷고 싶어" → 시간대가 없다 → "몇 시부터 몇 시까지요?"라고 되묻는다
    2. 동네 이름이 좌표로 바뀌지 않는다 → 다시 입력받는다
    3. 반경 안에 그 시간대에 맞는 스팟이 없다 → "이 시간대에 갈 만한 스팟이 없다"고 말한다

    셋 다 조용히 빈 동선을 내지 않고 이유를 보여 준다.

    추천 엔진은 외부 서비스를 모르는 모듈로 만든다. 엔진이 받는 것은 자연어가 아니라 해석이 끝난 구조화된 요청(시간대 · 좌표 · 선호 · 필수 스팟)이고, 문장을 그 모양으로 바꾸는 해석은 LLM 어댑터의 일이다. 시간대 필터 · 후보 선별 · 시간 배치 · 검증은 순수 규칙이고, LLM(해석 · 순서 제안) · TMAP · Geocoding · 저장은 바깥에서 꽂는 어댑터다. 외부 서비스가 하나도 없어도 구조화된 요청을 직접 주면 직선거리 추정으로 동선이 나오므로 테스트와 데모가 그 상태에서 돈다. TMAP 보행자 경로는 POST /tmap/routes/pedestrian에 출발 · 도착 · 경유지(passList, 최대 100개)를 넘기면 GeoJSON으로 totalDistance(m) · totalTime(초)와 경로 좌표열이 온다. 고도는 없다.
